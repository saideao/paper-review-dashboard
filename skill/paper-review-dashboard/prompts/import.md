你要把一批**已经写好的审稿意见**整理成一份可勾选的修改清单。目标会议是【会议名 / 期刊名，不知道就写"未注明"】。
附件有两样：论文全文【LaTeX 源码 / PDF】，和已有的审稿意见【从哪来的都行：会议或期刊返回的审稿意见、导师或合作者的批注、别的 AI 在聊天里给的一大段意见】。

你这次**不是审稿人**，是整理的人。意见是别人提的，你做四件事：拆开、对到原文、核对、给改法。
你只做分析，不要改写论文正文。

## 整理要求

1. **不加不减**。原来的意见里提到的每一点都要有一张卡片，一点都不能漏；你自己读论文时发现的新问题不要写进来。想让你也审一遍，是另一件事（见最后一节）。
2. **一条只说一件事**。一段话里说了三件事，就拆成三张卡片。几位审稿人说的是同一件事，合成一张，把每个人都写进来源。
3. **保留原话**。每张卡片逐字摘录提出者的原话，原文是英文就照抄英文，不翻译、不润色、不概括。原话很长就截最关键的一两句。
4. **对到原文**。回到论文里，找到这条意见说的是哪一句，逐字引用并写上页码。
   - 意见明确指了位置（第几节、哪张表）：引那里最相关的一句。
   - 意见是笼统的（比如"新意不够""实验不充分"）：找论文里最直接对应的那一句，比如贡献列表里的那条声明、实验设置里的那句。
   - 实在对不到任何一句：`quote` 留空，`location` 写"全文，未指明位置"。不要硬凑一句不相干的。
5. **回到论文核对**。提意见的人也会看漏、看错。每条给出四种判断之一，并用论文里的内容说明理由：
   - 成立：论文确实有这个问题；
   - 部分成立：有这个问题，但没有意见说的那么严重，或者只对了一半；
   - 不成立：论文里其实已经写了或做了，写清在哪一节、哪张表。这种情况往往是论文没写清楚，改法是让读者不再看漏，而不是什么都不做；
   - 无法判断：需要论文之外的信息（比如某篇你没读过的相关工作、作者手里的实验记录），写出要核对什么。
   不要因为提意见的人身份高就判成立，也不要为了让作者好受判不成立。
6. **给改法**。每条都要有修改思路和最小修复，写法和要求见下面的字段说明。需要新数据、新实验、新引用才能解决的，写进"需要作者补充"，不要替作者编数字、编结果、编文献。
7. **排优先级**：
   - P0：提出者明确说这是主要问题、影响评分、不解决就拒，或者你核对后确认是事实错误、逻辑矛盾、过度声称；
   - P1：改了能明显改善评价；
   - P2：小问题、建议性的意见、口味。
   同一条被好几个人提到的，往高排。
8. 提问也算意见。审稿人问"为什么不比较 X？"，就是一张卡片：论文里少了这个比较，或者少了一句不比较的理由。
9. 夸奖、总结性的话（"这篇论文研究了……""写得很清楚"）不做卡片，但在总览里用一句话带过。
10. 意见里指出的拼写、语法、格式小错，放进文字小错表，不做卡片。

## 输出格式：一份 JSON 数据

页面的样子是固定的：有一份现成的模板（`templates/dashboard.html`）负责排版和交互，你只输出数据。

```json
{
  "summary": { ... },
  "issues":  [ ... ],
  "claims":  [],
  "typos":   [ ... ]
}
```

### summary

- `mode`：固定写 `"import"`。模板靠它知道这是导入的意见。
- `title`：论文题目；`venue`：目标会议；`date`：整理日期（YYYY-MM-DD）。
- `sources`：字符串数组，每份意见一个名字，比如 `["审稿人 1", "审稿人 2", "导师"]`。意见里有编号或署名就照用，没有就按顺序起名。不要写真实姓名，除非用户要求。
- `verdict`：用一两句话说这些意见合起来是什么态度。意见里给了评分或结论就如实写（比如"三位审稿人给了 6、5、3，主要分歧在实验是否充分"）；没给就不要自己编一个评分。
- `scores`：空数组 `[]`。维度打分是审稿人的事，这里不打。
- `must_fix`：字符串数组，"最该先处理的几件事"，不超过 6 件，每件后面写卡片编号。
- `passes`：数组，一份意见一项，`{name, result}`。name 是来源的名字；result 写这份意见拆成了几条、其中几条对到了原文、几条没对到、各种核对结果各几条，以及有没有夸奖或总结性的话被略过。

### issues：修改卡片

一条意见一张卡片：

- `id`：R01、R02……
- `source`：谁提的。几个人都提了就写"审稿人 1、审稿人 3"。
- `said`：提出者的原话，逐字。几个人都提了，挑说得最具体的那位的话，前面注明是谁，比如"审稿人 3：The ablation ……"。
- `group`：类别，从这十个里选：声明与证据、数字一致性、方法学、实验、相关工作与引用、写作结构、术语与符号、图表、格式与匿名、口味项。
- `priority`：P0 / P1 / P2；`effort`：小 / 中 / 大。
- `title`：用一句话说清问题本身。
- `location`：这条意见对应论文的哪一节、哪一段。
- `page`：quote 所在的 PDF 页码（从 1 数起，按 PDF 文件的页序；没有 PDF 或 quote 为空时填 0）。
- `quote`：论文里对应的原句，逐字，最多两句。对不到就留空字符串。
- `stance`：成立 / 部分成立 / 不成立 / 无法判断，四种之一。
- `why`：核对的理由，两三句，要引到论文里的具体内容。"不成立"的写清论文哪里已经回答了；"无法判断"的写清要核对什么。
- `approach`："修改思路"。先说方向（收窄声明、补证据、补说明、改结构），要动哪几处，有没有别的可行方案和各自的代价。"不成立"的意见也要写：怎么改能让下一个读者不再看漏，或者写明"不用改，回复时指出第几节即可"。
- `fixes`："最小修复"，数组，每项 `{where, before, after}`。能改一句就不改一段；before 只截能在论文里唯一搜到的最短片段；after 要能直接贴回论文。纯文本，不加标记。
- `needs_author`："需要作者补充"。没有就是空字符串。

这次不用写 `attack` 字段，原话已经是审稿人的话了。

### claims

空数组 `[]`。声明—证据表是审稿时才做的。

### typos

意见里指出的文字小错。字段 `id`（T01……）、`location`、`page`、`quote`（论文原文，包住错处的最短片段）、`fix`、`type`（拼写 / 语法 / 标点 / 大小写 / LaTeX / 引用格式 / 其他）。意见里没有提就是空数组。

### 几条共同的要求

- `quote` 必须是论文里逐字能搜到的原句；`said` 必须是意见里逐字能搜到的原话。自检脚本两样都会核对。
- 所有字段都是纯文本，不要写 HTML 标签。提到别的条目时直接写编号（R03、T05）。
- 条目多也要全部写完，不要写"其余略"。
- 必须是合法的 JSON：字符串里的双引号写成 \"，反斜杠写成 \\。

最后只输出这一个 JSON（放在一个代码块里），不要在外面再写总结。

## 想同时让 AI 也审一遍

导入只整理别人的意见。如果还想知道这些意见之外有没有漏掉的问题：先用 `prompts/review.md` 让 AI 审一遍，得到另一份清单，再用 `prompts/cross.md` 把两份交叉汇总。导入得到的这份清单可以直接当作其中一位审稿人交进去。
