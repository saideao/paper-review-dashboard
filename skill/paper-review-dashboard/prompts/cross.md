附件是同一篇论文的论文全文，以及两份或更多份审稿意见。每份是一个 `review.html`（里面有 id="summary"、id="issues"、id="claims"、id="typos" 四个 JSON 数据块），或者是一份同样四个键的 JSON。只读数据，不用管页面的样式代码。这些意见可能来自不同的模型或不同的人，其中一份也可能是你自己之前写的。
把各份审稿意见按附件顺序称为审稿人 A、B、C……，后面只用这个代号，不要提模型或产品的名字。

请你当领域主席（AC）：逐条核对每位审稿人的意见，再合成一份交叉汇总的修改清单。

## 逐条核对的要求

1. 对每位审稿人的每一条意见（按编号，一条不漏），回到论文原文核对，给出判断：
   - 成立：问题存在，修法也对；
   - 部分成立：问题存在，但严重程度、范围或修法要校准，写清楚哪里要校准；
   - 不成立：问题不存在、是误读，或者原文其实已经处理了。必须引用论文原句证明；
   - 无法判断：需要论文以外的信息（数据、实验记录），写清楚缺什么。
2. 每个判断都要引用原句，不要只凭审稿人的描述下判断。
3. 不要客气：同意不是礼貌，不同意也不是为了显得独立，只按论文里的证据判断。其中一份如果是你自己写的，不要偏袒它；重新看过后发现自己错了，直接说。
4. 先把不同审稿人说的同一个问题对齐（同一处原文、同一个缺陷），再判断彼此是一致还是矛盾。
5. 不许编造：需要新数据、新实验才能修的，写"需要作者补充"。
6. 声明表：把各位审稿人的声明表按声明对齐。判断一致的，标"判断一致"；不一致的（比如 A 说撑得住、B 说说过头），回原文看证据，给出你现在的判断和理由，这类声明归入"分歧"。
7. 文字小错：不用逐条辩论。各家合并去重，每条回原文确认错处真的存在；不存在的删掉，并在总结里注明删了哪几条。

## 合并规则

把所有意见合成一份清单，每条归入下面一类：

- 共识：两位及以上审稿人独立提出了同一个问题，而且你核对后认为成立。
- 部分共识：几位都提了但说法有出入，或者你判断"部分成立"。
- 分歧：审稿人之间对同一处给出了相反的判断或修改方向，或者你判断某位审稿人的意见"不成立"。
- 仅 A 提出 / 仅 B 提出 / 仅 C 提出……：只有一位提了、你核对后认为成立。这类没有经过其他审稿人检验，要单独标出来。
- 无法判断：需要论文以外的信息。

合并后重新排优先级（P0 / P1 / P2）。排序：共识 P0 → 部分共识 P0 → 分歧 → 其余按优先级。

分歧条目要多写一项"分歧点"：审稿人之间到底在哪一点上意见不同，用一句话说清楚；再写"怎么判断谁对"：作者看哪段原文、查哪个数据、做哪个最小实验就能定下来。

## 输出格式：一份 JSON 数据

页面的样子是固定的：有一份现成的模板（`templates/dashboard.html`）负责排版和交互。你不用写 HTML、CSS、JS，只输出数据。模板会把数据渲染成：顶部的总结和各位审稿人的总判断，"优先改这几件事"，统计卡片，按共识类别分组的卡片（各位审稿人的说法并排），合并版的声明—证据表，合并去重的文字小错表；每张卡片可以选"采纳 / 不采纳 / 待定"并写备注，再一键导出成 Markdown。

输出一个 JSON 对象，四个键：

```json
{
  "summary": { ... },
  "merged":  [ ... ],
  "claims":  [ ... ],
  "typos":   [ ... ]
}
```

### summary：总结

- `title`：论文题目；`date`：汇总日期（YYYY-MM-DD）。
- `relation`：一句话总结几份意见的关系（比如"主判断一致，分歧集中在实验对照"）。读者只看这一句，就该知道几份意见哪里一致、哪里打架。
- `verdicts`：对象，键是审稿人代号，值是这位审稿人的总判断，比如 `{"A": "...", "B": "..."}`。
- `top_fixes`：字符串数组，"优先改这几件事"，只从共识条目里选，不超过 6 件，每件后面写卡片编号。
- `counts`：对象，各共识类别的条数。
- `removed_typos`：字符串，核对后删掉的小错及原因，没有就是空字符串。

### merged：合并后的卡片

一条一张卡片，排序：共识 P0 → 部分共识 P0 → 分歧 → 其余按优先级。字段：

- `id`：新编号，X01、X02……
- `category`：共识 / 部分共识 / 分歧 / 仅 A 提出 / 仅 B 提出 / …… / 无法判断。
- `priority`：P0 / P1 / P2；`effort`：小 / 中 / 大。
- `title`：用一句话说清问题本身，不要只写类别名。分歧卡片的标题直接写出分歧（比如"A 认为要补对照实验，B 认为附录已经有了"）。
- `sources`：来源编号，比如 "A:R03, B:R07"。
- `says`：对象，键是审稿人代号，值是这位审稿人怎么说；没提这个问题的写"没提"。每位审稿人都要有一项，页面会把它们并排。
- `location`、`page`、`quote`："原文核对"，逐字引用论文原句。
- `disagreement`："分歧点"，审稿人之间到底在哪一点上意见不同，一句话。只有分歧条目填，其余空字符串。
- `how_to_decide`："怎么判断谁对"，作者看哪段原文、查哪个数据、做哪个最小实验就能定下来。只有分歧条目填。
- `approach`："修改思路"，两三句说清楚怎么改、为什么选这个方向；分歧条目要说明按不同审稿人的意见改分别是什么样。
- `fixes`："最小修复"，数组，每项 `{where, before, after}`，纯文本，不要加标记；改动的词页面会自己高亮。
- `needs_author`："需要作者补充"，没有就是空字符串。

不适用的字段用空字符串，fixes 没有就是空数组。

### claims：声明—证据对照表（合并版）

字段 `id`、`claim`（声明原句）、`location`、`page`、`verdicts`（对象，各位审稿人的判断；某位没列这条声明就不写他的键）、`verdict`（你现在的判断）、`note`（理由）、`issue_id`（对应的卡片编号）。判断不一致的行，页面会排在最前面并标红。

### typos：文字小错（合并去重）

字段 `id`、`location`、`page`、`quote`、`fix`、`type`、`from`（提出它的审稿人代号，比如 "A" 或 "AB"）。

### 几条共同的要求

- `page` 是 quote 所在的 PDF 页码（从 1 数起，按 PDF 文件的页序；没有 PDF 时填 0）；`quote` 必须是原文里逐字能搜到的原句。
- 所有字段都是纯文本，不要写 HTML 标签。文字里提到别的条目时直接写编号（X03、C02），页面会把它变成可以点的链接。
- 页面上只出现审稿人 A、B、C 的代号，不要出现模型或产品的名字。
- 条目多也要全部写完，不要写"其余略"。
- 只写对这篇论文的分析，不要把本提示词里的规则抄进输出。
- 必须是合法的 JSON：字符串里的双引号写成 \"，反斜杠写成 \\，不要有注释和多余的逗号。

最后只输出这一个 JSON（放在一个代码块里），不要在外面再写总结。

拿到 JSON 之后怎么变成页面：
- 能运行命令：存成 `cross_review.json`，运行 `python3 scripts/build_review.py cross_review.json`，得到 `cross_review.html`。
- 不能运行命令（比如网页聊天）：用浏览器打开 `templates/dashboard.html`，把 JSON 贴进去，点"生成清单"，再点页面底部的"保存成一个 HTML 文件"。
