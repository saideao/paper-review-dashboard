# 论文修改看板（paper-review-dashboard）：论文审稿 → 修改清单

这个 skill 只做分析，不改论文正文。它不依赖任何特定的 agent 或模型：在哪个 agent、哪个聊天窗口里都能用。

| 用法 | 什么时候 | 输入 | 交给用户 |
|---|---|---|---|
| **审稿（默认）** | 用户要审一篇论文 | 论文 PDF 或 LaTeX 源码 | `review.html` |
| **交叉汇总** | 用户拿来两份或更多份审稿清单 | 论文 + 几份审稿 HTML | `cross_review.html` |

多模型交叉审稿的做法：用户在几个不同的 agent 或聊天模型里各用一次"审稿"，得到几份 `review.html`，再在任意一个 agent 里用"交叉汇总"合并。各份最好来自不同公司的模型。交付审稿结果时，可以提一句"想更稳的话，可以在别的模型里也审一遍，再让我交叉汇总"。

清单页面的样子是固定的：`templates/dashboard.html` 是现成的模板，负责排版和交互。**你只写数据（一份 JSON），不要自己写 HTML、CSS、JS**，再用 `scripts/build_review.py` 把数据装进模板。这样每次出来的页面都一样好看，你也不用把篇幅花在写页面上。

页面上有：顶部的总判断和"必须闭环的几件事"，统计卡片，左侧大纲可以跳转，卡片可以勾选"已处理"（刷新不丢），改前 / 改后自动高亮改动的词，浅色和深色。交叉汇总的页面还能给每条选"采纳 / 不采纳 / 待定"，再一键导出成 Markdown。

## 文件

- `prompts/review.md`：审稿要求。分六遍查：声明和证据对不对得上、方法实验、相关工作、写作结构、文字小错、格式匿名。还规定了输出数据的四个部分（summary / issues / claims / typos）和每个字段写什么。
- `prompts/cross.md`：交叉汇总要求。你当领域主席，逐条核对每位审稿人的意见，再合并成共识、部分共识、分歧、仅 A / 仅 B……、无法判断。
- `templates/dashboard.html`：固定的页面模板，审稿和交叉汇总共用。不要改它，也不要照着它重写一份。
- `scripts/build_review.py`：把 JSON 装进模板，写出 `review.html` 或 `cross_review.html`。只用 Python 标准库。
- `examples/`：一篇虚构论文的示例数据和生成好的页面，可以打开看效果、对照字段怎么填。
- `scripts/check_review.py`：自检清单（`.html` 和 `.json` 都能查）：数据块齐不齐、修改思路和最小修复有没有填全、原文引用能不能在论文里逐字找到。只用 Python 标准库，不改文件。

## 审稿（默认）

1. **确认论文和会议**。拿到论文和目标会议，没有会议就用"本领域的顶会"。
   - PDF 和 LaTeX 源码都可以。两者都有时以 PDF 为准写页码。
   - 有实验记录、数据表的话，一起拿来，用来核对论文里的数字。

2. **读 `prompts/review.md`，按它审稿。** 那份文件就是给审稿人的完整要求，你就是那个审稿人。
   - 把【会议名】这类占位换成实际内容，然后逐条照做；
   - 六遍检查一遍都不能跳；
   - 原文必须逐字引用，有 PDF 时写上 PDF 页码（按 PDF 文件的页序，从 1 数起）；
   - 每条意见都要有修改思路和最小修复。

   读 PDF 时能直接读就直接读。能运行命令、又装了 `pdftotext` 的话，可以用 `pdftotext -layout` 抽一份文字方便检索，但引用原句以 PDF 为准，抽取产生的断行和连字符不算论文的错。

3. **把数据写成 `review.json`，放在论文旁边，再生成页面**：

   ```bash
   python3 <skill>/scripts/build_review.py review.json     # 写出 review.html
   ```

   - 四个部分要完整，条目多也要全部写完，不要写"其余略"。
   - 不能运行 Python 但能写文件：把 `templates/dashboard.html` 复制成 `review.html`，把里面 `id="summary"`、`id="issues"`、`id="claims"`、`id="typos"` 四个数据块的内容换成你的数据，并删掉空的 `id="merged"` 那一块。别的地方一个字都不要动。
   - 不能写文件（比如网页聊天）：把 JSON 输出给用户，告诉他用浏览器打开 `templates/dashboard.html`，把 JSON 贴进去，点"生成清单"，再点页面底部的"保存成一个 HTML 文件"。

4. **自检**（能运行 Python 时）：

   ```bash
   python3 <skill>/scripts/check_review.py review.html 论文.pdf
   ```

   - 打印条目数、各优先级条数、缺修改思路或最小修复的条目、没有对应卡片的问题声明，以及原文引用逐字对上几条。
   - 有 ✗ 的就补上；对不上的引用回去对照原文改成逐字原句，再跑一次。跨栏、跨页的个别条目对不上没关系。
   - 不能运行 Python 时跳过这一步，自己回头核一遍引用。

5. **交给用户**。给出文件路径，用两三句话说出总判断和最该先改的几条（P0）。

## 交叉汇总

1. **收齐材料**：论文，加两份或更多份审稿结果（用这个 skill 或 `prompts/review.md` 生成的 `review.html`，或者同样内容的 JSON）。读 HTML 时只看里面的四个 JSON 数据块，不用管样式代码。按用户给的顺序叫它们审稿人 A、B、C……，页面上不出现模型名字。如果其中一份是你自己写的，也一视同仁。

2. **读 `prompts/cross.md`，按它汇总。** 你当领域主席：
   - 每位审稿人的每一条都回到原文核对，给出成立、部分成立、不成立或无法判断，并引用原句；
   - 对齐不同审稿人说的同一个问题，再分成共识 / 部分共识 / 分歧 / 仅 A / 仅 B…… / 无法判断；
   - 分歧条目写出分歧点和"怎么判断谁对"。

   不要因为多数人这么说就判它成立：共识只用来决定先改哪条，对不对要看论文里的证据。

3. **把数据写成 `cross_review.json`，生成页面**，然后自检：

   ```bash
   python3 <skill>/scripts/build_review.py cross_review.json   # 写出 cross_review.html
   ```


   ```bash
   python3 <skill>/scripts/check_review.py cross_review.html 论文.pdf
   ```

4. **交给用户**，并说明：
   - 先改共识；
   - 分歧条目里写了"怎么判断谁对"；
   - 每条可以选"采纳 / 不采纳 / 待定"，再用"导出我的决定"导出成 Markdown，贴回来，你就只改采纳的条目。

## 注意

- 不要修改论文文件，也不要用审稿意见直接改论文。改论文要等用户明确说开始，而且只改用户选定的条目。
- 审稿结果里出现"需要作者补充"的地方，是要用户自己提供的材料，不要替用户编数据、编实验、编引用。
- 清单页面是纯离线的单文件 HTML，不联网，不上传。
